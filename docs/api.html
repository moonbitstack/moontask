pub fn chain(Array[Sig]) -> Sig

| The runs in sigs, in order, each one started when the one before it succeeds.

A chain of chains is flattened, so chain([a, chain([b, c])]) is a → b → c. Building a chain publishes nothing.

pub fn chord(Array[Sig], Sig) -> Sig

| The runs in parts, then callback once every part has succeeded.

The callback is sent with the list of part results as its argument, in the order the parts were given. Every part carries the same key and the same list of ids, so the part that finishes last can collect the set by itself.

A part that fails for good does not hold the chord open: the last part to finish records the callback as failed, so nobody waits on a callback that will never be sent.

pub let chunk_name : String

| The name a chunk runs under.

One body serves every worker, so a chunk published by one process is run by a worker in another: the message names the task the chunk is of, and the body that runs it comes with the worker rather than from whoever built the canvas.

pub fn group(Array[Sig]) -> Sig

| Every run in sigs, all at once, waited on together.

A chain given to a group is not broken up: its head is published and its tail travels with it, so the group waits on the chain's last link. The handle's value is the list of results in the order the sigs were given.

pub struct Dispatch {
  • appApp
  • queueString
  • }

| The executor a state graph runs on: every work item of a superstep becomes a queue message, and what comes back is the write that step contributes.

A graph keeps the order, the durability and the retry policy of a run; this only decides where a node's body runs. Here it runs on the workers, so a workflow outlives the process that started it.

Which task a node runs, and what it is called with, is the app's route for its graph and node, which is what a flow registers: a node that waits for nothing is called with the run's input, and a node that waits for others with an object of their answers under their ids. A node with no route writes nothing, and a graph with several roots uses one such node as its entry.

pub struct Task[A, R] {
  • appApp
  • nameString
  • policyPolicy
  • runasync (A, Context) -> R
  • }

| A registered body. Sending it writes a message and hands back a handle.

The argument type is what the body takes; the result type is what it returns, and the handle decodes the stored value back into it. Both go over the wire as JSON, so a task may be sent by one process and run by another.

pub fn[A, R, B : @json.ToJson] Task::chunks(Self[A, R], Array[B], size? : Int32) -> Sig raise @spec.Refused

| The runs of tuples, size of them per run, all at once.

A part of the group is one run of the chunk task, which runs its slice of the tuples one after another in the worker that picked it up and answers their results in order. The handle answers one list per part, so the results of the whole fan-out are those lists in order; the last part holds what is left over.

Batching trades parallelism for dispatch: one message per size runs is fewer broker round trips and fewer reservations.

A slice is one run of the chunk task, so it is retried as a whole by that task's policy — the default one, since the message names the chunk task and not the task inside it — and a tuple that fails stops its slice. A run that needs its own retry budget is sent with map or starmap instead, where each run carries the policy of the task it belongs to.

pub fn[A : @json.ToJson, R] Task::map(Self[A, R], Array[A]) -> Sig

| One run of this task per item, all at once: a group whose parts are the items in the order they were given.

Each item is the whole argument of its run, so a task that takes a record is mapped over records. The handle answers the results in that same order, and an empty list is a group with nothing to wait for, which answers an empty list rather than refusing.

pub struct Scheduler {

  • jobsArray[Job]

| A set of jobs and the clock they run against.

The scheduler holds no queue and no store: a job that must survive a restart, run on another machine, or be retried belongs on a task instead. What it does keep is the rhythm — the next run of each job is computed from the run that was due, not from the moment the loop happened to wake, so a loop that was busy for a while does not drag every job with it.

| A workflow.

The order of the steps is the order they were registered, and the graph is derived from it: a step runs once every step it waits for has answered, and steps that wait for nothing run together. What each step answers is kept in the run's state, keyed by its id, and a step that waits for others is called with an object of their answers — under their ids — as its argument.

A flow does not run anything itself: run hands the steps to an app's workers, and the graph that orders them is a state graph, so a run that stops halfway can be resumed where it stopped.
