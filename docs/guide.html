From one task to a queue across processes.

This walks the library in the order it is used: a task that runs, a worker that runs it, what happens when it fails, what happens after it succeeds, how steps come to depend on each other, and how to move the whole thing onto a server and into a database.

  1. Install and import

    Add the package and import the two names you need first. Time is always a function you pass in: the library never reads the system clock, which is what makes the examples below reproducible.

    moon add moonbitstack/moontask
    import {
  "moonbitstack/moontask",
  "moonbitstack/moontask/spec",
}

  2. An app, a task, a worker

    The app owns three things: where messages go (Broker), where results go (Backend), and what counts the parts of a chord (Counter). The in-memory broker is all three at once, which is enough to run the whole library in one process.

    let clock : Clock = { at: 1_700_000_000_000L }
let now = fn() { clock.at }
let broker = @moontask.MemoryBroker::new(clock=now)
let app = @moontask.App::new(broker, backend=broker, counter=broker, clock=now)

let greet = app.task("greet", fn(name : String, ctx : @moontask.Context) {
  "hello \{name}, attempt \{ctx.attempt}"
})

let worker = app.worker(concurrency=2)
@async.with_task_group(async fn(group) {
  group.spawn_bg(async fn() { worker.run() }, no_wait=true)
  let handle = greet.send("ada")
  println(handle.get(timeout=5000L))
  worker.stop()
})

    It prints:

    hello ada, attempt 1

  3. Declaring a task with an annotation

    #task.def on a function declares a task, the way a decorator does: the generator reads the function's signature and writes a typed handle for it, so a producer sends it without spelling the name again. The function may be plain or async, takes the one value its message carries, and may end with the run's Context.

    #task.def(name="orders.place", queue="orders", retries="1")
pub fn place(order : Order, ctx : @moontask.Context) -> String raise {
  if ctx.attempt == 1 && order.cups > 9 {
    fail("too many cups for one try")
  }
  "\{order.id}: \{order.cups} cups on attempt \{ctx.attempt}"
}

    The options are name (the function's own name when left out), queue, retries, timeout (250ms, 30s, 5m or 1h), acks_late and ignore_result; they are laid over the app's preset, and anything else is set by calling App::task directly. The generator writes one register_tasks for the package, which registers everything it declared and hands back the handles:

    let tasks = register_tasks(app)
let receipt = tasks.place.send({ id: "b2", cups: 12, })
println(receipt.get(timeout=5000L))

    It is a build step rather than a macro, so the generated file is readable MoonBit and the editor sees the types: a rule in moon.mod, and one line in the package's moon.pkg saying which file it reads and which it writes.

    rule(name: "tasks", command: "moonx moonbitstack/moontask/cmd/tasks -C \"$mod_dir\" \"$input\" -o \"$output\"")
    dev_build(rule: "tasks", input: "jobs.mbt", output: "jobs.g.mbt")
formatter(ignore: [ "jobs.g.mbt" ])

    Both tasks above come from one file; the first attempt of the large order fails and the retry the annotation allowed runs, so the transcript shows both the policy and the attempt counter:

    registered tick, orders.place
queue      orders, retries 1
answer     a1: 2 cups on attempt 1
answer     b2: 12 cups on attempt 2
tick       done

  4. When a run fails

    A task body that raises is recorded, not lost. Inside the retry budget the message is published again with an eta computed from the policy's backoff; past the budget the failure is what the store keeps. The spread inside an exponential backoff is derived from the task id, so the same task waits the same on every machine and a test can assert the delay.

    let flaky = app.task("flaky", fn(_ : Unit, _) -> Unit raise {
  attempts.push(1)
  if attempts.length() < 2 {
    fail("not yet")
  }
}, policy={ ..@moontask.policy, retries: 2, backoff: @moontask.Backoff::Fixed(delay=1000L) })

    Between the two attempts the handle reports RETRY; once the second attempt returns it reports SUCCESS:

    state   RETRY
state   SUCCESS
attempts 2

    The policy also says how long one run may take (timeout), whether the message is confirmed before or after the run (acks_late), whether the result is kept (ignore_result) and how fast the task may go (rate).

  5. What happens after a run succeeds

    A chain is one message carrying its own tail; a group is several messages published together; a chord counts its parts and sends one callback. The worker that finishes last is the one that advances the canvas, so there is no coordinator to run.

    let chained = @moontask.chain([step.sig(1), step.sig(2), step.sig(3)]).send(app)
println(chained.get(timeout=5000L).stringify())          // 30
let grouped = @moontask.group([step.sig(4), step.sig(5)]).send(app)
println(grouped.get(timeout=5000L).stringify())          // [40,50]
let joined = @moontask.chord([step.sig(1), step.sig(2), step.sig(3)], total.sig([])).send(app)
println(joined.get(timeout=5000L).stringify())           // 60

    The chord's callback is sent with the list of part results, in the order the parts were given. A part that fails for good records the callback as failed instead of leaving it pending forever.

    A fan-out is the same shape at a larger size: a map sends one run per item, a starmap one per tuple — the tuple spread across that run's arguments — and a chunk one message per slice of tuples, which the worker that took it runs in order.

    println(step.map([1, 2, 3]).send(app).get(timeout=5000L).stringify())
println(total.starmap([[1, 2], [3, 4]]).send(app).get(timeout=5000L).stringify())
println(step.chunks([[1], [2], [3], [4], [5]], size=2).send(app).get(timeout=5000L).stringify())

    Three lists, in the order the items were given — the last one a list per slice, the final slice holding what is left:

    [10,20,30]
[3,7]
[[10,20],[30,40],[50]]

    A tuple of one is that argument and a longer tuple is the argument list, which is the same reading a consumer on the other side of a shared queue gets, so a fan-out published here is runnable there. An empty fan-out publishes nothing and answers an empty list.

  6. Steps that depend on each other

    A flow is a set of steps and the dependencies between them. Each step is an ordinary task, so it runs wherever a worker picks it up; the order comes from a state graph, and each run carries the logical instant it belongs to rather than the time it happened to start.

    let flow = @flow.Flow::new("etl", schedule=@moontask.Schedule::Every(interval=3_600_000L))
flow.step("extract", extract)
flow.step("load", load, deps=["extract"])
let run = flow.run(app, 1_700_000_000_000L)
println(run.thread)                       // etl:1700000000000
println(run.output_of("load").unwrap().stringify())

    A step that waits for nothing is called with the run's input; a step that waits for others is called with an object of their answers under their ids. A step may name only steps registered before it, which keeps the flow acyclic by construction, and steps that wait for nothing run in the same superstep — on as many workers as are listening.

    A backfill walks a window of the schedule, one run per instant, and a failed run does not stop the ones behind it. Catch-up does the same from the last run the flow knows about, which is how a scheduler that was down for an hour comes back without losing the hour:

    let runs = flow.backfill(app, start=0L, end=3L * 3_600_000L)   // three runs
let caught = flow.catchup(app, now=7L * 3_600_000L)

    Give the flow a saver and an interrupted run resumes at the step it stopped on; give it a recorder and every run is written as it ends:

    flow.keep(@moonstate.MemorySaver::new())
flow.record(store)

  7. On a rhythm

    A beat sends tasks on a schedule: every interval, on a cron boundary, or once at an instant.

    let beat = app.beat()
beat.add("tick", tick, (), @moontask.Schedule::Every(interval=1000L))
beat.add("nightly", report, (), @moontask.Schedule::Cron(@cron.parse("0 0 2 * * *")))

group.spawn_bg(async fn() { beat.run() }, no_wait=true)

    Inside a single process, without a broker, a scheduler runs a job on the same kind of rhythm:

    let scheduler = @schedule.Scheduler::new(clock=now)
scheduler.add(@schedule.every(10).minutes().at(":30").run(fn() { sweep() }))
scheduler.run()

    The next run is computed from the run that was due, not from the moment the loop woke, so a loop that was busy for a while does not drag the rhythm with it.

  8. Across processes

    The Redis module implements the same three contracts, so the app above changes in one line. A queue is a list per name; messages waiting for their eta sit in a sorted set; each consumer keeps what it holds in a list of its own, kept alive by a lease.

    let conn = @socket.Connection::connect(@moonredis.ClientOptions::at("127.0.0.1", 6379))
let broker = @redis.Broker::new(conn, clock=now, consumer="worker-7")
let app = @moontask.App::new(broker, backend=broker.store(), counter=broker.store(), clock=now)

    A worker that dies stops refreshing its lease. recover hands the work it was holding back to the queue, which is what makes a killed worker's tasks run again:

    println(broker.recover())   // messages moved back to their queues

    The same module can speak Celery's layout instead, so one queue can be worked from both sides. The ready list, the envelope, the reservation table and a chord's join keys then belong to Celery, and either side can run what the other published — and hand back what a worker on the other side left behind:

    let broker = @redis.Broker::celery(conn, clock=now, consumer="worker-7")

  9. Results and history in a database

    The SQL module is a result store and a run recorder on one connection, over any moondb driver, so the same code runs on SQLite, MySQL and PostgreSQL. Nothing in it opens a socket: the driver is yours.

    let store = @sql.Store::new(conn, clock=now)
store.ensure()                                        // once, at start-up
let app = @moontask.App::new(broker, backend=store, clock=now)
flow.record(store)

    A database that answers in the same call has a driver of that shape, and Store::inline takes it — a statement against a local file runs where it was made, and everything above it is the same code:

    let db = @sqlite.SqliteDriver::open("queue.db")
let store = @sql.Store::inline(db, clock=now)

    Two tables, one row per run and one row per workflow run. A write is a single upsert, so a worker killed mid-write leaves the previous state rather than half of the new one; the runs of a flow read back newest first, and a run that failed reads back with the words it failed with.

    let kept = store.runs("etl", limit=10)
println(kept[0].at)                                    // the newest instant
println(kept[0].status.code())                         // SUCCESS or FAILURE

    The table names are a record, so two queues can share one schema without mixing their rows.

  10. A page over the queue

    The management module answers the same questions over HTTP, and is an ASGI application rather than a server of its own, so a server runs it and a framework mounts it.

    let admin = @admin.Admin::new(app, inspector=broker)
let asgi = admin.to_asgi()
// GET  /                 the page
// GET  /api/tasks        what is registered, and how each runs
// GET  /api/queues       ready, delayed and unconfirmed counts
// GET  /api/results/{id} the state of one run
// POST /api/tasks/{name} send a run
// GET  /api/events       a stream of counts

  11. Writing a broker

    A transport implements Broker and the library runs on it unchanged. Four calls: publish, claim, confirm, reject. The receipt the claim hands back is opaque to the library — a sequence number, a log entry, whatever the transport needs to settle the message later.

    pub(open) trait Broker {
  async fn publish(Self, queue : String, message : Message) -> Unit raise Refused
  async fn consume(Self, queues : ArrayView[String], prefetch~ : Int32) -> Delivery raise Refused
  async fn ack(Self, delivery : Delivery) -> Unit raise Refused
  async fn reject(Self, delivery : Delivery, requeue~ : Bool) -> Unit raise Refused
}
